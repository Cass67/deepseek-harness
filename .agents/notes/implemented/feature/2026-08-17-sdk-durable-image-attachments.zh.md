# Agent Note: SDK 持久图像附件

Status: implemented

[English](2026-08-17-sdk-durable-image-attachments.md) | 中文

## 问题

独立 JSON-RPC SDK 客户端可以在提示词中提交 `ImageAttachmentRef`，却没有创建该引用的协议操作。让客户端自行构造引用会暴露后端身份规则，而在每个提示词内发送临时字节会绕过持久附件服务，使模型可见历史缺少经过验证的对象。

## 决策

SDK 协议提供进程级 `attachment/imageLimits` 和 `attachment/saveImage` 方法。限制响应报告当前附件服务策略。保存请求携带非空、规范且带填充的 base64、声明的 `ImageMediaType` 与可选显示名称；结果为服务持有的 `ImageAttachmentRef`。

服务器通过 `ctx.get('attachments')` 解析可选服务；服务缺失时，两个方法都以明确的能力缺失错误失败。服务器校验精确请求字段及服务支持的媒体类型，在分配解码字节前根据 `maxImageBytes` 限制 base64 字符长度，拒绝无法往返为完全相同规范字符串的编码，检查解码后的字节长度，并把发布交给 `AttachmentStore.saveImage`。提示词排队前，服务器通过当前服务递归读取每个已提交的图像引用，要求返回的规范元数据完全匹配，并对经过验证的存储字节应用 `maxImagesPerMessage` 和 `maxMessageImageBytes`。任何失败都不会创建提示词及其会话。完整栅格解码、声明类型与检测类型的一致性、像素限制、名称清理、内容寻址及持久发布仍由提供方负责。

TypeScript 与 Python 提供对应的底层和高层图像限制及保存操作。客户端对字节执行规范编码，并严格校验引用的每个字段；返回的字节长度和媒体类型还必须与请求一致。附件 ID 保持不透明，返回的显示名称可以由提供方清理或省略。

发布的 JSON-RPC 组合挂载 `@deepseek-ai/dsh-attachment-local`。其根目录遵循 `DSH_HOME`，绝不默认使用工作区或会话目录，使仅所有者可访问的内容寻址存储独立于会话持久化。

## 模型可见验证

无密钥 `image-attachment` SDK 快照启动真实 JSON-RPC 组合，上传 PNG，将返回引用放入图像块，并使用显式声明支持图像输入的 `llm-replay` 模型运行。持久 `user/message` 固定进入组装模型历史的同一持久引用，快照控制输出固定限制与上传元数据。该快照覆盖持久 SDK 准入与回放，而非真实提供方序列化。`dsh-llm-pi-ai` 包测试另行覆盖图像能力适配器的附件解析与原生图像转换；这里不声称存在已组装的真实提供方图像快照。

## 考虑过的替代方案

**在 `session/prompt` 内内联 base64。** 这会在提示词接纳中重复上传校验、扩大重复流量，并使选择会话前准备内容的客户端无法创建持久引用。

**数据 URL 或宽松 base64。** 多种等价写法会增加字节限制与请求身份判断的复杂度。规范且带填充的 base64 只有一种协议表示，并允许服务器在解码前拒绝过大的文本。

**由客户端推导内容哈希。** 本地存储目前使用 SHA-256 ID，但服务接口有意保持附件 ID 不透明，使其他提供方可以选择不同的持久身份。

## 后果

SDK 客户端可以一次准备一个持久图像，并在会话输入中复用其类型化引用。上传或提示词接纳失败发生在持久排队之前，提供方仍对图像检查与持久发布具有权威。base64 会扩大协议数据，每次上传只保存一个图像而非批次，自定义 JSON-RPC 组合必须挂载附件服务才能提供该能力。
